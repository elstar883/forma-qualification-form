# Как внести вклад

Спасибо за интерес к «FORMA». Это небольшое локальное приложение, поэтому главные
требования — сохранять согласованные правила квалификации честными, а интерфейс —
предсказуемым.

## 1. Ветки

- `main` — стабильная версия, ветка по умолчанию;
- `develop` — интеграционная ветка;
- `feature/<краткое-имя>` — новая функциональность;
- `fix/<краткое-имя>` — исправление;
- `docs/<краткое-имя>` — документация.

Ветки создаются от `develop`, завершённая работа вливается в `develop`, затем
`develop` — в `main` через merge-коммит.

## 2. Коммиты

Используются Conventional Commits:

```text
feat: add the six-step qualification form
fix: keep the first invalid field focused after validation
docs: describe the qualification rules
test: cover the eight sample leads and storage recovery
chore: add editor configuration
```

Сообщение — в императиве, на английском; тело коммита объясняет причину
изменения, если она не очевидна.

## 3. Локальные проверки

```bash
node scripts/validate.mjs
node --check app/js/app.js
make serve
```

Перед PR все проверки должны проходить. CI повторит их на Node.js 18, 20 и 22.

## 4. Правила для данных и требований

- `references/` — исходные материалы и согласованное ТЗ, не редактируйте их в PR;
- все имена, телефоны, суммы и адреса остаются демонстрационными;
- обязательных полей должно оставаться 9, необязательных — 3;
- шагов формы должно оставаться 6;
- словари значений и тексты сообщений меняются только в `app/js/config.js`;
- статусы и причины меняются только в `app/js/qualification.js`;
- необязательные поля не должны влиять на статус;
- статус и слова «Не наш формат», «отказ», «неподходящий» не должны появляться на
  клиентских экранах;
- ключи `localStorage` не переименовывайте без обновления документации.

Если меняется модель данных или правило квалификации, обновите
`docs/DATA-MODEL.md`, `docs/QUALIFICATION-RULES.md`, `README.md` и
`scripts/validate.mjs`.

## 5. Правила для приложения

- только HTML, CSS и современный JavaScript без фреймворков;
- без сборщиков и runtime-зависимостей;
- без сетевых запросов, внешних шрифтов, CDN и аналитики;
- интерфейс на русском языке;
- сохраняйте доступность: семантическая разметка, подписи, видимый фокус,
  поддержку клавиатуры, `aria-live` у динамических сообщений;
- проверяйте ширину 1440, 768, 390 и 360 px;
- не добавляйте секреты, локальные артефакты и реальные персональные данные.

## 6. Процесс OpenCode

Проект собран по воспроизводимой методике:

1. `/forma-plan` — план экранов, полей, правил и состояний без изменения файлов;
2. человек подтверждает спорные правила и объём этапа;
3. `/forma-build` — Build меняет только `app/`;
4. `/forma-qa` — независимый аудит без автоматических исправлений;
5. исправления — только после согласования.

Методика описана в
[`.opencode/skills/forma-qualification-form/SKILL.md`](.opencode/skills/forma-qualification-form/SKILL.md),
правила проекта — в [`AGENTS.md`](AGENTS.md).

## 7. PR-чек-лист

- [ ] изменение соответствует задаче;
- [ ] `node scripts/validate.mjs` проходит;
- [ ] `node --check app/js/app.js` проходит;
- [ ] `references/` не изменены;
- [ ] данные остаются демонстрационными;
- [ ] статус не появляется на клиентских экранах;
- [ ] проверены desktop, 768, 390 и 360 px;
- [ ] проверены клавиатура и видимый фокус;
- [ ] обновлены README или docs, если изменилось поведение;
- [ ] в PR нет секретов, архивов, PDF и `.DS_Store`.
